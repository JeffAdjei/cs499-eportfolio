3D Graphics Rendering Project (CS 330)

Narrative · Original & Enhanced Artifact Reflection

What the artifact is

The artifact is an OpenGL 3D scene I built for CS 330 Computational Graphics & Visualization. The original project composed a small indoor scene from primitive meshes, loaded textures, and rendered the result through a simple camera and a single scene manager. It relied on a monolithic main loop with repeated rendering calls and hard-coded input handling.

Why I included it

I selected this artifact for the algorithms and data structures category because graphics work is fundamentally about how data and operations are organized for efficient, repeatable execution. The project gave me a concrete setting to practice separating concerns, eliminating redundancy, and structuring per-frame work around reusable abstractions — exactly the kind of algorithmic thinking I wanted to demonstrate.

Enhancements

Rendering PipelineRender stages separated so per-object logic is called through a clear flow rather than inlined in main.
Reduced RedundancyShared mesh setup and camera math extracted into dedicated ShapeMeshes and camera modules.
Scene OrganizationSceneManager owns object lifecycle; ViewManager owns window + view. Clean ownership boundaries.
Input HandlingInput-to-camera mapping refactored so adding a new control type does not require touching the render loop.

Course outcomes demonstrated

  • Outcome 3 — Design & evaluate computing solutionsRestructuring the render pipeline and scene/view/mesh responsibilities shows algorithmic evaluation of trade-offs in how rendering data is organized.
  • Outcome 4 — Innovative techniques, skills & toolsApplying data-structure thinking (ownership, reuse, separation of concerns) to a graphics pipeline using OpenGL and GLFW.
  • Outcome 1 — Collaborative environmentsThe refactor makes the codebase friendlier for another engineer to extend — new shapes or cameras no longer require touching unrelated code.
  • Outcome 2 — Professional communicationHeader comments, module boundaries, and this narrative communicate the design intent behind each change.

Reflection on the process

The hardest part of this enhancement was resisting the temptation to treat graphics code as a single script just because the scene was visually small. Once I accepted that repeated setup code and monolithic loops were structural problems, the refactor became straightforward: name the responsibilities, give each one a home, and let the render flow call into them. I came away with a much stronger instinct for when duplication signals a missing abstraction rather than a harmless shortcut, which is a habit I will carry into larger systems.
